# GitHub Actions for SDETs — Course Contents

**Goal:** Understand, configure, secure, and troubleshoot CI workflows for software validation.

**Prerequisites:** Git, GitHub repositories, YAML, and basic shell commands.

**Scope:** GitHub Actions concepts and operations, independent of any particular test framework.

## 1. GitHub Actions Fundamentals

- Continuous integration and continuous delivery concepts
- Workflows, events, jobs, steps, actions, and runners
- Workflow files in `.github/workflows/`
- Workflow execution from trigger to completion
- GitHub Actions UI: runs, jobs, logs, and summaries
- Workflow status versus individual job and step results

## 2. Workflow Structure and YAML

| --- | --- |

### Practice Topics

- YAML indentation, mappings, lists, strings, and multiline values

- Workflow-level, job-level, and step-level configuration

## 3. Events and Triggers

| Event or Filter | Purpose |
| --- | --- |
| `push` | Run on pushes to matching branches or tags |
| `pull_request` | Run for selected pull request activity |
| `workflow_dispatch` | Start a workflow manually with optional inputs |
| `schedule` | Trigger scheduled runs using cron syntax |
| `workflow_call` | Make a workflow callable by another workflow |
| `workflow_run` | Trigger in response to another workflow's execution |
| `repository_dispatch` | Trigger through an external API event |
| `branches` / `branches-ignore` | Filter applicable branch events |
| `paths` / `paths-ignore` | Filter applicable events by changed paths |
| `tags` / `tags-ignore` | Filter push events by tag |
| `types` | Select activity types supported by an event |

### Practice Topics

- Choosing push, pull request, manual, and scheduled triggers
- Understanding pull request base-branch filters
- Avoiding duplicate push and pull request runs
- Understanding default-branch requirements for manual and scheduled workflows
- Understanding why scheduled runs may start later than expected
- Security implications of `pull_request_target` and workflows that consume untrusted code

## 7. Variables, Secrets, and Contexts

| Syntax or File | Purpose |
| --- | --- |

## 14. Workflow Management with GitHub CLI

**Prerequisite:** Install GitHub CLI (`gh`), authenticate, and run these commands in the intended repository or supply `--repo OWNER/REPO`.

| Command | Purpose |
| --- | --- |
| `gh auth status` | Check CLI authentication |
| `gh workflow list` | List workflows |
| `gh workflow view <workflow>` | Inspect a workflow |
| `gh workflow run <workflow> --ref <branch>` | Trigger a workflow supporting manual dispatch |
| `gh workflow run <workflow> -f environment=test` | Pass a defined manual input named environment |
| `gh run list --workflow <workflow>` | List workflow runs |
| `gh run view <run-id>` | Inspect a run and its jobs |
| `gh run view <run-id> --log-failed` | Read logs from failed steps |
| `gh run watch <run-id> --exit-status` | Wait for a run and return failure if it fails |
| `gh run download <run-id> --dir artifacts` | Download run artifacts |
| `gh run rerun <run-id> --failed` | Rerun failed jobs |
| `gh run cancel <run-id>` | Cancel a run |

## 15. Troubleshooting

- Workflow missing or not triggered
- Incorrect event, branch, path, or activity filters
- Invalid YAML or unsupported keyword placement
- Jobs stuck waiting for a runner or environment approval
- Checkout, dependency installation, and authentication failures
- Incorrect working directories and missing files
- Missing configuration or unavailable secrets
- Permission-denied errors from GITHUB_TOKEN
- Flaky service startup and network connectivity
- Timeouts, cancellation, and matrix fail-fast behavior
- Missing artifacts and incorrect report paths
- Tests failing while the pipeline incorrectly reports success
- Differences between local and runner environments

## 16. SDET Practical Exercises

1. Read an existing workflow and explain its trigger, jobs, dependencies, and expected outputs.
2. Create a validation workflow triggered by a pull request and manual dispatch.
3. Add inputs for selecting a test environment.
4. Run independent checks in parallel and combine their results in a downstream job.
5. Use a matrix to validate across two runtime versions.
6. Publish reports on failure while preserving the failed workflow result.
7. Add dependency caching and verify cache-hit and cache-miss behavior.
8. Start a database service container and wait for readiness before validation.
9. Extract repeated logic into a reusable workflow or composite action.
10. Restrict token permissions and diagnose a deliberately missing permission.
11. Cancel an obsolete run when a new commit arrives on the same branch.
12. Inspect, rerun, and download artifacts from a failed run using GitHub CLI.

**Suggested learning order:** Fundamentals and YAML → triggers → jobs and steps → runners and configuration → conditions and matrix → artifacts and services → reuse and security → troubleshooting.

## 17. Playwright Project Setup

**Project:** Build a GitHub Actions pipeline for a Playwright Test project using TypeScript.

### Project Structure

```text
playwright-ci-project/
├── .github/
│   └── workflows/
│       └── playwright.yml
├── tests/
│   ├── smoke.spec.ts
│   └── regression.spec.ts
├── playwright.config.ts
├── package.json
├── package-lock.json
└── .gitignore
```

### Topics

- Initialize a Playwright Test project.
- Create smoke and regression tests against a practice application.
- Configure the base URL through `BASE_URL`.
- Define Chromium, Firefox, and WebKit projects.
- Configure CI retries, worker counts, and timeouts.
- Enable HTML reporting and failure diagnostics: traces, screenshots, and videos.
- Exclude dependencies, generated reports, and authentication state from source control.
- Commit the dependency lockfile for reproducible installation.

| Command | Purpose |
| --- | --- |
| `npm init playwright@latest` | Scaffold a Playwright project |
| `npm ci` | Install dependencies from the committed lockfile |
| `npx playwright install --with-deps` | Install browsers and required system dependencies on a supported runner |
| `npx playwright test` | Run all tests |
| `npx playwright test --project=chromium` | Run the configured Chromium project |
| `npx playwright test tests/smoke.spec.ts` | Run the smoke test file |
| `npx playwright test --grep @smoke` | Run tests tagged or titled with @smoke |
| `npx playwright show-report` | Open the generated HTML report locally |
| `npx playwright show-trace <trace.zip>` | Open a downloaded trace locally |

## 18. Playwright CI Workflow

### Pipeline Stages

1. Trigger on pull requests, selected branch pushes, or manual dispatch.
2. Check out the repository.
3. Set up the project's supported Node.js version.
4. Install dependencies with `npm ci`.
5. Install the required Playwright browsers and system dependencies.
6. Start the practice application or select an accessible deployed environment.
7. Wait for application readiness.
8. Run the selected Playwright suite.
9. Upload reports and diagnostic artifacts, including after test failure.
10. Preserve the test command's failure result in the workflow status.

### Workflow Configuration Topics

| Item | Project Requirement |
| --- | --- |
| Runner | Use a supported Linux runner for the initial project |
| Pull request checks | Run the smoke suite for fast feedback |
| Scheduled execution | Run the full regression suite |
| Manual inputs | Select a suite and target environment |
| Environment variables | Pass `BASE_URL` into the Playwright configuration |
| Secrets | Supply test account credentials without logging them |
| Permissions | Start with `contents: read` and add permissions only when needed |
| Timeout | Set a job timeout suitable for the suite |
| Concurrency | Cancel obsolete runs for the same pull request |
| Failure handling | Keep test failures visible while collecting diagnostics |

## 19. Playwright Reports and Failure Analysis

- Upload `playwright-report/` for HTML results.
- Upload `test-results/` for configured traces, screenshots, and videos.
- Give artifacts distinct names for each browser or shard.
- Configure artifact retention and missing-file behavior.
- Download artifacts through the Actions UI or GitHub CLI.
- Distinguish assertion failures from application availability, browser setup, and runner failures.
- Investigate retries and flaky tests without treating retries as the underlying fix.
- Review reports for credentials or sensitive application data before retaining them.

| Command | Purpose |
| --- | --- |
| `gh run view <run-id> --log-failed` | Inspect failed workflow steps |
| `gh run download <run-id> --dir artifacts` | Download reports and diagnostics |
| `npx playwright show-report <report-directory>` | Open a downloaded HTML report |
| `npx playwright show-trace <trace.zip>` | Investigate actions, timing, and failures in a trace |

## 20. Playwright Parallel Execution and Sharding

- Distinguish Playwright workers within a job from matrix jobs across runners.
- Distribute a growing suite across shards.
- Use a GitHub Actions matrix to supply shard indexes.
- Avoid overlapping test data and shared account conflicts.
- Generate a separate blob report for each shard.
- Upload shard reports with unique artifact names.
- Merge downloaded blob reports into one HTML report in a downstream job.
- Preserve failed-shard status while allowing report aggregation.

| Command | Purpose |
| --- | --- |
| `npx playwright test --workers=2` | Limit worker parallelism within one runner |
| `npx playwright test --shard=1/3 --reporter=blob` | Run the first of three shards and generate a mergeable report |
| `npx playwright merge-reports --reporter=html ./all-blob-reports` | Generate an HTML report from collected blob reports |

## 21. Playwright Project Completion Criteria

- A pull request automatically runs smoke tests.
- A manual run accepts the intended suite and environment inputs.
- A scheduled run executes regression tests.
- Failed assertions cause the workflow to fail.
- Reports and configured diagnostics remain downloadable after failures.
- A contributor can diagnose an intentionally introduced test failure from the artifacts.
- Parallel runs use isolated test data and uniquely named artifacts.
- A sharded run produces a consolidated report.
- Credentials remain outside source control and logs.
- The project README explains local execution, workflow triggers, inputs, and report retrieval.

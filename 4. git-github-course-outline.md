# Git and GitHub — Course Contents

## 1. Git and GitHub Fundamentals

- Version control and its purpose
- Git versus GitHub
- Local repositories and remote repositories
- Working directory, staging area, and commit history
- Commits, branches, tags, and HEAD
- Basic workflow: change → stage → commit → push → pull request

## 2. Installation and Configuration

| Command | Purpose |
| --- | --- |
| `git --version` | Check the installed Git version |
| `git config --global user.name "Your Name"` | Set the author name for commits |
| `git config --global user.email "you@example.com"` | Set the author email for commits |
| `git config --global init.defaultBranch main` | Set the initial branch name for new repositories |
| `git config --list --show-origin` | Inspect configuration values and their sources |
| `git config user.email "project@example.com"` | Override the email for the current repository |
| `git help <command>` | Open command documentation |

### Topics

- System, global, and repository configuration scopes
- Commit identity versus GitHub authentication
- HTTPS credentials and SSH keys
- Keeping private keys and access tokens out of repositories

## 3. Creating and Cloning Repositories

| Command | Purpose |
| --- | --- |
| `git init` | Initialize a repository in the current folder |
| `git clone <repository-url>` | Clone a remote repository |
| `git clone <repository-url> <folder>` | Clone into a selected folder |
| `git status` | Inspect branch and file status |
| `git status --short` | Show compact file status |
| `git rev-parse --show-toplevel` | Locate the repository root |

### Topics

- The .git directory
- Creating a repository on GitHub
- Cloning an existing project versus publishing a local project
- Tracked, untracked, modified, staged, and ignored files

## 4. Staging and Committing Changes

| Command | Purpose |
| --- | --- |
| `git add <file>` | Stage a file's current changes |
| `git add .` | Stage changes under the current directory |
| `git add -p` | Select individual change hunks to stage |
| `git restore --staged <file>` | Unstage a file while retaining working changes |
| `git commit -m "Describe the change"` | Commit staged changes |
| `git commit --amend` | Replace the latest commit with an amended commit |
| `git mv <old-path> <new-path>` | Move a tracked file and stage the change |
| `git rm <file>` | Remove a tracked file from the working directory and stage deletion |

### Topics

- Small, focused commits
- Clear commit messages
- Reviewing staged content before committing
- Why editing a file after staging requires staging the new changes again
- Amending unpublished commits and coordinating changes to shared history

## 5. Comparing Changes

| Command | Purpose |
| --- | --- |
| `git diff` | Compare working changes with the staging area |
| `git diff --staged` | Compare staged changes with HEAD |
| `git diff HEAD` | Compare tracked working content with HEAD |
| `git diff <commit-a> <commit-b>` | Compare two snapshots |
| `git diff main...feature/login` | Show feature-branch changes since the common ancestor |
| `git diff --stat` | Summarize changed files and line counts |
| `git diff --check` | Check changes for whitespace errors |

## 6. Viewing History

| Command | Purpose |
| --- | --- |
| `git log` | View commit history |
| `git log --oneline` | Show a compact history |
| `git log --oneline --graph --decorate --all` | Visualize branch history |
| `git log -- <file>` | View commits affecting a file |
| `git show <commit>` | Inspect a commit and its changes |
| `git blame <file>` | Identify commits associated with lines |
| `git reflog` | Inspect locally recorded reference movements |

### Topics

- Commit hashes and parent commits
- HEAD, HEAD~1, and relative revision references
- Understanding a change using its diff and surrounding history
- Reflog as local recovery information, with limited retention

## 7. Branches

| Command | Purpose |
| --- | --- |
| `git branch` | List local branches |
| `git branch -a` | List local and remote-tracking branches |
| `git switch -c feature/login` | Create and switch to a branch |
| `git switch main` | Switch to an existing branch |
| `git branch -m <new-name>` | Rename the current branch |
| `git branch -d <branch>` | Delete a branch when Git's merged-history checks allow it |
| `git branch -vv` | Inspect branch tracking and commit information |

### Topics

- Feature, fix, and release branch conventions
- Local branches versus remote-tracking branches
- Upstream tracking relationships
- Detached HEAD and creating a branch to retain new work

## 8. Remote Repositories, Fetch, Pull, and Push

| Command | Purpose |
| --- | --- |
| `git remote -v` | List remotes and URLs |
| `git remote add origin <repository-url>` | Add a remote named origin |
| `git remote set-url origin <repository-url>` | Update the origin URL |
| `git fetch origin` | Download remote objects and update remote-tracking references |
| `git fetch --prune origin` | Also remove stale remote-tracking references |
| `git pull --ff-only` | Update only if a fast-forward is possible |
| `git pull --rebase` | Fetch and replay local commits onto the fetched upstream |
| `git push -u origin feature/login` | Push a branch and establish upstream tracking |
| `git push` | Push according to the configured tracking and push settings |
| `git push origin --delete <branch>` | Delete a remote branch |

### Topics

- Fetch versus pull
- Ahead, behind, and diverged branches
- Fast-forward updates and rejected pushes
- Inspecting incoming changes before integrating them
- Pull configuration and team conventions

## 9. Merging and Conflict Resolution

| Command | Purpose |
| --- | --- |
| `git merge feature/login` | Merge the named branch into the current branch |
| `git merge --no-ff feature/login` | Create a merge commit even when fast-forwarding is possible |
| `git status` | Identify conflicted files |
| `git diff` | Inspect conflicting or resolved changes |
| `git add <resolved-file>` | Stage a resolved file |
| `git merge --continue` | Complete a merge after resolution |
| `git merge --abort` | Attempt to abandon the current merge and restore pre-merge state |

### Topics

- Fast-forward versus three-way merge
- Conflict markers and competing changes
- Resolving conflicts using the command line or editor
- Reviewing the combined behavior after a resolution
- Running relevant checks before completing the merge

## 10. Rebasing and Cherry-Picking

| Command | Purpose |
| --- | --- |
| `git rebase main` | Replay current-branch commits onto main |
| `git rebase -i HEAD~3` | Interactively edit the last three commits when that ancestry exists |
| `git rebase --continue` | Continue after resolving and staging conflicts |
| `git rebase --abort` | Abandon the rebase |
| `git cherry-pick <commit>` | Apply a selected commit's change to the current branch |
| `git cherry-pick --continue` | Continue after resolving conflicts |
| `git cherry-pick --abort` | Abandon the cherry-pick operation |

### Topics

- Merge versus rebase
- Reword, reorder, squash, and fixup operations
- Why rebasing changes commit identities
- Coordination before rewriting shared history
- Applying a fix to another branch without merging the whole branch

## 11. Stashing Work

| Command | Purpose |
| --- | --- |
| `git stash push -m "Work in progress"` | Save tracked working and staged changes temporarily |
| `git stash push -u -m "Include new files"` | Also include untracked files, excluding ignored files |
| `git stash list` | List saved stashes |
| `git stash show -p 'stash@{0}'` | Inspect a stash patch |
| `git stash apply 'stash@{0}'` | Apply a stash while retaining it |
| `git stash pop` | Apply the latest stash and remove it if application succeeds |
| `git stash drop 'stash@{0}'` | Delete a saved stash |

### Topics

- Temporarily switching tasks
- Apply versus pop
- Conflicts while restoring a stash
- Stash as temporary local storage, not a shared backup

## 12. Undoing Changes and Recovery

| Command | Purpose |
| --- | --- |
| `git restore <file>` | Discard unstaged changes in a tracked file, restoring from the index |
| `git restore --staged <file>` | Unstage changes without discarding working content |
| `git revert <commit>` | Create a new commit reversing an earlier commit's changes |
| `git reset --soft HEAD~1` | Move back one commit while keeping changes staged |
| `git reset --mixed HEAD~1` | Move back one commit while keeping changes in the working directory |
| `git reflog` | Find earlier local reference positions |
| `git branch recovery/<name> <commit>` | Retain a reachable commit on a recovery branch |

### Topics

- Restore versus reset versus revert
- Reverting published changes without rewriting shared history
- Recovering an accidentally moved branch
- Understanding that hard reset discards tracked working changes
- Reflog cannot recover every discarded uncommitted edit
- Force push versus force-with-lease and why either requires care with shared work

## 13. Ignoring Files with .gitignore

- Ignoring dependencies, build outputs, reports, and local settings
- Protecting credentials, saved authentication state, and environment files
- Directory patterns, wildcard patterns, and exceptions
- Why .gitignore does not stop tracking files already committed

| Command | Purpose |
| --- | --- |
| `git check-ignore -v <file>` | Identify the matching ignore rule |
| `git status --ignored` | Inspect ignored files |
| `git rm --cached <file>` | Stop tracking a file while retaining the working copy |

### Example for a Playwright Project

```gitignore
node_modules/
playwright-report/
test-results/
playwright/.auth/
.env
.env.*
!.env.example
```

Commit package-lock.json for reproducible installs. A previously exposed credential must be revoked or rotated; ignoring or deleting its file does not remove earlier copies from history.

## 16. Pull Requests and Code Review

- Base branch versus head branch
- Opening draft and ready-for-review pull requests
- Writing a useful title, description, and validation summary
- Reviewing changed files and leaving line comments
- Requesting changes, updating commits, and resolving conversations
- Connecting issues and pull requests
- Merge commits, squash merging, and rebase merging
- Deleting completed feature branches
- Understanding required checks and merge conflicts

### Practical Workflow

1. Update the local main branch.
2. Create a feature branch.
3. Make, inspect, and commit a focused change.
4. Push the branch and open a pull request.
5. Address review feedback and failed checks.
6. Merge using the repository's agreed method.
7. Update local main and remove the completed branch.

## 17. Forks and Upstream Synchronization

- Forking versus cloning versus branching
- Origin as your fork and upstream as the source repository
- Synchronizing a fork without overwriting local work
- Creating a pull request across repositories

| Command | Purpose |
| --- | --- |
| `git remote add upstream <source-repository-url>` | Add the source repository as upstream |
| `git fetch upstream` | Download source repository changes |
| `git switch main` | Select the local main branch |
| `git merge --ff-only upstream/main` | Fast-forward main if its history allows it |
| `git push origin main` | Update the fork's main branch |

If main has diverged, inspect the histories and deliberately choose a merge or rebase instead of assuming a fast-forward is possible.

## 19. SDET Project Practice

- Create a repository for a test automation project.
- Add a README, .gitignore, and committed dependency lockfile.
- Create separate feature branches for UI tests and API tests.
- Stage selected changes and write focused commit messages.
- Open a pull request with a description and test evidence.
- Resolve a deliberate conflict in a test configuration file.
- Use a stash while switching to an urgent fix.
- Revert a faulty committed change on a practice branch.
- Tag a stable version of the framework.
- Inspect CI checks and failed-run logs in the GitHub web interface.

# Kubernetes for SDETs — In-Depth Course Contents

**Goal:** Understand Kubernetes architecture, inspect application environments, diagnose failures, and validate deployments, connectivity, configuration, and recovery behavior.

**Prerequisites:** Linux commands, Docker fundamentals, YAML, and basic HTTP, DNS, and networking concepts.

**Command convention:** Replace values such as `<pod>`, `<deployment>`, and `<file.yaml>` with actual names. Namespaced examples use a practice namespace named `sdet`. Perform mutation and failure exercises in a dedicated practice environment.

## 1. Kubernetes Architecture

- Cluster, control plane, and worker nodes
- API server: authentication, authorization, and admission
- etcd: cluster state storage
- Scheduler: selecting a node for a Pod
- Controller manager and reconciliation loops
- Kubelet: managing Pods on a node
- Container runtime and Container Runtime Interface (CRI)
- Cluster networking: CNI plugins and Service traffic handling
- CoreDNS and cluster name resolution
- Desired state versus actual state
- Resource creation flow: kubectl → API server → controllers and scheduler → kubelet

| Command | Purpose |
| --- | --- |
| `kubectl cluster-info` | View cluster endpoints |
| `kubectl get nodes -o wide` | View nodes, addresses, and runtime information |
| `kubectl get pods -n kube-system` | Inspect visible cluster system components |
| `kubectl api-resources` | List supported resource types |
| `kubectl api-versions` | List API versions available in the cluster |

## 17. Logs, Events, and Troubleshooting

- Logs versus events versus metrics
- Application failures versus infrastructure failures
- Pending: resources, scheduling constraints, or storage
- ImagePullBackOff: image names, registry access, or credentials
- CrashLoopBackOff: process crashes, configuration, or probes
- OOMKilled: memory usage and limits
- Running but not Ready: probe or dependency failure
- Service unavailable: selectors, endpoints, ports, DNS, or policies
- Storage failures: binding, attachment, mount, or permissions
- Rollout failures: unhealthy new replicas or incompatible configuration

## 18. SDET Practical Validation Scenarios

1. Deploy an application and trace its Deployment → ReplicaSet → Pods → Service relationships.
2. Replace a Pod and verify application recovery and replica restoration.
3. Update the image, observe the rollout, introduce a bad image, and recover through rollback.
4. Break a Service selector or target port, diagnose the connection failure, and restore it.
5. Test DNS resolution within a namespace and across namespaces.
6. Update configuration and compare environment-variable behavior with mounted-file behavior.
7. Replace a Pod and verify persistent data remains available through its PVC.
8. Introduce an invalid image, startup failure, and readiness failure; identify their distinct symptoms.
9. Set restrictive resource requests or limits and distinguish scheduling failures from runtime failures.
10. Apply a NetworkPolicy and verify allowed and denied connections where enforcement is supported.
11. Check that an account can inspect required resources but cannot perform unauthorized mutations.
12. Diagnose an Ingress routing failure by checking the controller, Service, and backend Pods.
13. Observe autoscaling under controlled load when the required metrics are configured.
14. Collect logs, events, resource definitions, and reproduction steps for a useful defect report.

**Suggested learning order:** Architecture and kubectl → Pods and controllers → Services and networking → configuration and storage → resources and health → scaling and security → Helm and troubleshooting.
